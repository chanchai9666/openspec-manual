คู่มือการใช้งาน OpenSpec ฉบับใช้งานจริง (Unofficial v1.x)

สรุปครบถ้วนเรื่อง Spec-Driven Development (SDD) — วิธีสั่งงาน AI Coding Assistant ให้ได้ผลลัพธ์ที่ตรงจุด มีเอกสารสเปกตรวจสอบย้อนกลับได้ และลดความผิดพลาด โดยการสร้าง "ชั้นข้อตกลง (Agreement Layer)" ตกลงรายละเอียดสเปก สถาปัตยกรรม และงาน ก่อนเริ่มเขียนโค้ด

1 สรุปภาพรวม & แนวคิด Spec-Driven Development (SDD)

OpenSpec เป็นโอเพนซอร์สมาตรฐานที่ช่วยยกระดับการทำงานกับ AI Coding Assistant จากการเขียนโค้ดแบบเดาสุ่ม (Vibe Coding) มาสู่กระบวนการที่รัดกุมผ่านแนวคิด Spec-Driven Development (SDD) โดยเปลี่ยน Specification ให้กลายเป็นสิ่งที่ "ตรวจสอบได้ (Executable)" และเป็นพิมพ์เขียวที่ AI ใช้สร้างโค้ดตามลำดับ

🎯 Agreement Layer

ตกลงขอบเขต พฤติกรรม และเงื่อนไขที่ยอมรับได้ (Acceptance Criteria) กับ AI ให้เรียบร้อยในไฟล์ Markdown ก่อนแตะต้องโค้ด

🛡️ ป้องกัน Scope Drift

AI จะไม่แอบเพิ่มฟังก์ชันนอกเหนือความต้องการ ไม่หลุดสเปก และไม่ทำลายโค้ดเดิมที่มีอยู่แล้ว

🧹 แก้ปัญหา Context ล้น

แยกขั้นตอนคิด (Explore/Propose) ออกจากขั้นตอนทำ (Apply) ทำให้สามารถเปิด New Clean Session สำหรับเขียนโค้ดได้เสมอ

📖 Living Documentation

สเปกในโฟลเดอร์ openspec/specs/ จะถูกรวมเข้าและเติบโตตามโค้ดจริง กลายเป็นเอกสารระบบที่ไม่มีวันล้าสมัย

2 ข้อกำหนดของระบบ & การติดตั้ง CLI

ข้อกำหนดของระบบ (Prerequisites)

  • Node.js: เวอร์ชัน v20.19.0 ขึ้นไป (ตรวจสอบด้วย node --version)
  • ระบบปฏิบัติการ: macOS, Linux, Windows
  • AI Coding Assistants ที่รองรับ: Antigravity, Claude Code, Cursor, GitHub Copilot, Cline, Devin, Gemini CLI, Roo Code ฯลฯ

วิธีการติดตั้ง CLI ลงในเครื่อง

npm (วิธีแนะนำทั่วไป) 
npm install -g @fission-ai/openspec@latest
Homebrew (macOS และ Linux) 
brew install openspec
Bun, Deno หรือ Nix 
# Bun (ยังต้องมี Node runtime ในเครื่อง)
bun install -g @fission-ai/openspec@latest

# Deno
deno install --global --allow-read --allow-write --allow-env --allow-sys=cpus,homedir --allow-net=edge.openspec.dev npm:@fission-ai/openspec@latest

# Nix Flake
nix profile install github:Fission-AI/OpenSpec
⚡ ติดตั้งผ่าน AI Chat Prompt
ส่งข้อความนี้ในช่องแชทของ AI เพื่อให้ AI ติดตั้งและตรวจสอบสภาพแวดล้อมให้อัตโนมัติ:

Fetch https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/install.md and follow it.

3 คำสั่ง 2 ประเภทที่ต้องแยกให้ชัด (Terminal CLI vs AI Agent Chat)

สิ่งที่ผู้เริ่มต้นมักสับสนคือการแยกระหว่าง คำสั่งใน Terminal กับ คำสั่งในช่องแชทของ AI ซึ่งมีหน้าที่และบริบทที่ต่างกันโดยสิ้นเชิง:

1. CLI Commands (Terminal / Console)

รันใน Terminal หรือ Command Prompt

ใช้สำหรับเตรียมโปรเจกต์, ดู Dashboard, ตรวจสอบความถูกต้อง, และจัดการสเปกระดับเครื่อง

# รันใน Terminal ของระบบ
openspec init --tools antigravity
openspec list --specs
openspec view
openspec validate add-auth
openspec archive add-auth
2. Agentic Commands (Chat / Skill)

พิมพ์ใน ช่องแชทของ AI Coding Assistant

ใช้สำหรับสั่งงาน AI ควบคุมวงจรการวางแผน การสร้างสเปก และการเขียนโค้ด

# พิมพ์ในหน้าต่างแชทของ AI
/opsx-explore rate-limiting
/opsx-propose add-rate-limiting
/opsx-apply add-rate-limiting
/opsx-archive add-rate-limiting

4 เริ่มต้นโปรเจกต์ใหม่แบบด่วน (Quickstart 1-2-3-4)

กระบวนการเริ่มต้นใช้งาน OpenSpec ตั้งแต่ศูนย์จนถึงส่งมอบงานแรก มีเพียง 4 ขั้นตอน:

1. ติดตั้ง CLI และสร้างโปรเจกต์

Terminal 
npm install -g @fission-ai/openspec@latest
cd my-project
openspec init --tools antigravity,cursor

คำแนะนำ: รีสตาร์ต IDE ของคุณ 1 ครั้งเพื่อให้ AI โหลดคำสั่ง Workflows ใหม่เข้ามา

2. สั่ง AI ร่างสเปกและแผนงาน (Propose)

AI Chat 
/opsx-propose add-rate-limiting
# หรือพิมพ์ภาษาธรรมชาติ:
Propose a change to add IP-based rate limiting to our API.

AI จะสร้างเอกสารวางแผนใน openspec/changes/add-rate-limiting/ โดยยังไม่แตะต้องโค้ด

3. ตรวจทานแผน (Review) และสั่งลงมือทำ (Apply)

เปิดอ่านไฟล์ tasks.md เพื่อตรวจสอบรายการงาน จากนั้นเปิด New Chat Session แล้วสั่ง:

AI Chat 
/opsx-apply add-rate-limiting
# หรือพิมพ์:
Apply the add-rate-limiting change.

4. ส่งมอบงานและจัดเก็บประวัติ (Archive)

AI Chat หรือ Terminal 
/opsx-archive add-rate-limiting
# หรือใน Terminal:
openspec archive add-rate-limiting

ระบบจะรวมความต้องการเข้าสู่ openspec/specs/ และย้ายงานเข้า archive/ จบวงจรสมบูรณ์

5 ลำดับวงจรการทำงาน (แบบเต็ม vs แบบย่อ & Quality Gates)

1
Explore

ระดมความคิด วิเคราะห์ทางเลือก (ห้ามเขียนโค้ด)

2
Propose

สร้าง Change Proposal & Delta Specs

3
Review

มนุษย์ตรวจสอบและแก้ไขสเปก

4
Apply

เขียนโค้ดตาม Tasks ทีละข้อ

5
Archive

รวมสเปกเข้า Main Specs & เก็บประวัติ

🔍 3 ด่านตรวจคุณภาพ (Quality Gates) ใน Workflow แบบเต็ม

Gate 1: Review Specs (ตรวจสเปก)

ตรวจสอบในไฟล์ specs/ ว่าความต้องการมีคำว่า SHALL และ Scenarios WHEN/THEN ครอบคลุมพฤติกรรมที่ยอมรับได้ครบถ้วนหรือไม่

Gate 2: Tasks Sign-Off (ตรวจเช็กลิสต์)

ตรวจทาน tasks.md ว่าแตกงานย่อยตรงตามสเปก ไม่มีงานส่วนเกิน และแบ่งขนาดไม่เกิน 15-30 นาทีต่องาน

Gate 3: Archive Verification (ตรวจก่อนรวม)

รัน openspec validate เพื่อยืนยันว่าโครงสร้างถูกต้องทุกข้อ และทุก Task ถูกติ๊กถูก [x] ครบถ้วนก่อนสั่ง Archive

ตารางเปรียบเทียบกระบวนการ: แบบเต็ม vs แบบย่อ

มิติเปรียบเทียบ Workflow แบบเต็ม (Full Loop) Workflow แบบย่อ (Lite / Fast-Track)
สถานการณ์ที่เหมาะ ฟีเจอร์ใหญ่, ระบบแกนกลาง, เปลี่ยน Database Schema, ระบบชำระเงิน/ความปลอดภัย งานแก้บั๊ก (Hotfix/Bugfix), ปรับ UI เล็กน้อย, เพิ่ม validation ฟิลด์เดียว, Prototype
ขั้นตอน Explore → Propose → Review → Apply → Verify → Archive Propose / Fast-Forward → Quick Review → Apply → Archive
Artifacts ที่สร้าง ครบ 4 ไฟล์ (proposal, specs, design, tasks) ย่อขนาด (proposal, specs, tasks โดยข้าม design.md)
เวลาเฉลี่ย 30 นาที – 2 ชั่วโมงต่อ Change 5 – 15 นาทีต่อ Change

6 เจาะลึกคำสั่ง Agent Skills (10 คำสั่งหลัก)

รายละเอียดสัญญาการทำงาน (Skill Contracts) ที่ AI Coding Assistant ใช้:

ชื่อ Skill ประเภท หน้าที่หลัก สิ่งที่สร้าง (Creates)
openspec-explore Core สำรวจและคิดร่วมกันก่อนวางแผน (ไม่เขียนโค้ด) สรุปไอเดียในแชท (บันทึกเมื่อขอ)
openspec-propose Core ร่าง Change Proposal พร้อมเอกสาร 4 ชิ้นครบชุด openspec/changes/<name>/
openspec-apply-change Core ลงมือเขียนโค้ดตามรายการเช็กลิสต์ใน tasks.md แก้ไขโค้ดจริงในโปรเจกต์
openspec-update-change Core ปรับปรุงแผนงานเมื่อสเปกหรือข้อตกลงเปลี่ยน อัปเดตไฟล์ Artifacts เดิม
openspec-sync-specs Core ผสานเฉพาะ Delta Specs เข้า Main Specs ระหว่างทาง อัปเดต openspec/specs/
openspec-archive-change Core ตรวจงานครบ รวม Delta เข้า Main และย้ายเข้า Archive อัปเดต specs/ และย้ายโฟลเดอร์
openspec-verify-change Optional ตรวจสอบโค้ดที่สร้างขึ้นเทียบกับข้อกำหนดในสเปก รายงานผลการ Verify
openspec-ff-change Optional สร้างเอกสารวางแผนทั้งหมดแบบ Fast-Forward รวดเดียว สร้างทุก Artifact ใน Pass เดียว
openspec-bulk-archive-change Optional ส่งมอบและรวมหลาย Change Proposals พร้อมกัน ย้ายหลายโฟลเดอร์เข้า Archive
openspec-onboard Optional เวิร์กโฟลว์สอนผู้ใช้ใหม่ด้วยการจำลองทำ 1 Change ตัวอย่าง Change จำลอง

7 เคล็ดลับการเขียน Prompt และสั่งงาน AI

💡 ทริคที่ 1: เจาะจงที่ What & Why

ในคำสั่ง Propose ให้อธิบายปัญหาและผลลัพธ์ที่ต้องการ ไม่จำเป็นต้องสั่งภาษาโค้ด ปล่อยให้ AI ออกแบบใน design.md

💡 ทริคที่ 2: ใช้คำสั่ง New Session สำหรับ Apply

เมื่อตรวจทานแผนเสร็จ ให้ปิดแชทเดิมแล้วเปิดหน้าต่างแชทใหม่ พิมพ์ Apply the <change> change. เพื่อให้ AI มี Context สะอาด 100%

💡 ทริคที่ 3: สั่งแก้ที่ไฟล์แผนงานเสมอ

หากโค้ดไม่ตรงใจ อย่าสั่งให้ AI แก้โค้ดมั่ว ให้สั่ง: "Update tasks.md to include error handling for timeout, then resume apply."

💡 ทริคที่ 4: สั่งให้ถามก่อนเริ่ม (Interview Pattern)

สั่ง AI ว่า: "Before proposing, ask me 3 clarifying questions about the edge cases."

8 แนวทางปฏิบัติที่ดี (Best Practices & กฎเหล็ก)

  • Right-Sizing: ซอย Change Proposal ให้มีขนาด 3-7 Tasks (ประมาณ 30 นาทีถึง 1 ชั่วโมงของเนื้องาน)
  • กฎเหล็กของสเปก: ทุก Requirement ต้องมี SHALL และมีอย่างน้อย 2 Scenarios (Happy path 1 ข้อ และ Error path 1 ข้อ)
  • Commit openspec/ เข้า Git สม่ำเสมอ: ให้เพื่อนร่วมทีมเห็นประวัติและเหตุผลของการออกแบบทั้งหมด
  • ห้ามข้ามขั้นตอนการ Review: การตรวจเอกสารใช้เวลา 30 วินาที แต่การแก้โค้ดที่ทำผิดทิศทางใช้เวลาหลายชั่วโมง

9 โปรเจกต์ใหม่ตั้งแต่ศูนย์ (Greenfield 0-to-1 Step-by-Step)

ตัวอย่างการเริ่มสร้างแอป Task Tracker จากโฟลเดอร์ว่างเปล่า:

ขั้นตอนที่ 1: เริ่มต้นโปรเจกต์ 
mkdir task-tracker && cd task-tracker
openspec init --tools antigravity,cursor
ขั้นตอนที่ 2: ใช้ Explore ให้ AI ช่วยเลือก Stack 
Help me explore a task tracker app from scratch. I haven't picked a stack yet.
Compare options (e.g. Node vs Python, SQLite vs In-memory) and recommend the best starting point.
ขั้นตอนที่ 3: สั่ง Propose Change แรกสำหรับ Core Model 
Propose a change to create the initial task data model and SQLite schema.
ขั้นตอนที่ 4: Apply ใน New Session แล้ว Archive 
Apply the create-task-model change.
# เมื่อเสร็จสิ้น:
Archive the create-task-model change.

ผลลัพธ์: เกิดไฟล์ Main Spec แรกที่ openspec/specs/tasks/spec.md เป็นพิมพ์เขียวให้ฟีเจอร์ถัดไป

10 โปรเจกต์เดิมที่มีโค้ดอยู่แล้ว (Brownfield & Incremental Adoption)

⚠️ กฎเหล็กของ Brownfield: "อย่าต้มน้ำทั้งมหาสมุทร (Don't boil the ocean)"
ห้ามพยายามให้ AI สแกนโค้ดทั้งแสนบรรทัดเพื่อเขียน Spec ให้ทั้งระบบในวันแรก! ให้ใช้กลยุทธ์ Incremental Adoption โดยให้สเปกค่อย ๆ งอกตามฟีเจอร์หรืองานแก้บั๊กที่เกิดขึ้นจริง

ตัวอย่าง: มีระบบ E-Commerce เดิม ต้องการ เพิ่มระบบคูปองส่วนลดในขั้นตอน Checkout:

  1. Initialize ในโปรเจกต์เดิม: openspec init --tools antigravity (โค้ดเดิมปลอดภัย 100%)
  2. ทำ Impact Analysis ด้วย Explore: 
    Help me explore adding coupon codes. Investigate `src/services/checkout.ts`. What are the regression risks?
  3. สร้าง Delta Spec เฉพาะจุดที่กระทบ: สเปกจะระบุ ADDED (คูปอง) และ MODIFIED (การคิดราคารวม)
  4. Apply เฉพาะจุด & Archive: โค้ดเดิมไม่พัง และเกิดไฟล์ openspec/specs/checkout/spec.md ขึ้นเป็นชิ้นแรกของระบบเดิม

11 การจัดการ & อัปเดตสเปก (Delta Specs System)

ในแต่ละ Change Proposal ไฟล์สเปกจะระบุเฉพาะส่วนที่เปลี่ยนแปลง แบ่งเป็น 4 หมวดหมู่:

Delta Spec Format 
# Delta Spec: Checkout System

## ADDED Requirements
### Requirement: Coupon Code Validation
The system SHALL validate expiration date and minimum spend for coupons.

## MODIFIED Requirements
### Requirement: Order Total Calculation
The system SHALL subtract discount amount before applying VAT.

## REMOVED Requirements
### Requirement: Legacy Promo Flags

## RENAMED Requirements
- FROM: `Requirement: Basic Cart`
- TO: `Requirement: Standard Cart`

12 รวมตัวอย่างจริงและกรณีศึกษา

🔐 Authentication (OAuth2)

ตัวอย่างการวางสเปก Google & GitHub Login พร้อมเงื่อนไข Token Refresh และ CSRF Protection

⏱️ Tiered Rate Limiting

ระบบจำกัดความถี่การเรียก API แยกตามระดับสิทธิ์ผู้ใช้ (Anonymous: 60/min, Pro: 1000/min)

💳 Stripe Payment Intent

สเปกระบบชำระเงินพร้อมดักจับ Webhook events และการจัดการกรณีบัตรถูกปฏิเสธ

🔄 Database Migration

การปรับโครงสร้างตารางข้อมูลขนาดใหญ่โดยไม่เกิด Downtime (Zero-downtime migration)

15 โครงสร้างไฟล์ในโปรเจกต์ & การตั้งค่า `config.yaml`

openspec/config.yaml 
schema: spec-driven

context: |
  Tech Stack: Next.js 15, TypeScript, Tailwind CSS, PostgreSQL.
  Testing: Vitest for unit tests, Playwright for E2E.
  Code Style: Functional components, strict type-checking, zero any.

rules:
  proposal:
    - Focus heavily on business impact and edge cases.
  specs:
    - Write at least 2 scenarios (1 happy path, 1 failure) per requirement.
  tasks:
    - Keep each task small and actionable (under 20 mins of work).

operations:
  apply:
    - Run `npm test` after modifying core logic.

16 Multi-Repo Architecture (Stores & Worksets)

สำหรับองค์กรที่มีหลาย Git Repositories แต่ต้องการแชร์สเปกและการวางแผนร่วมกัน:

การสร้างและผูก Store กลาง 
# 1. สร้าง Store กลางในเครื่อง
openspec store create platform-specs ~/workspace/platform-specs

# 2. ใน Repo ลูกแต่ละตัว ใส่บรรทัดนี้ใน openspec/config.yaml:
store: platform-specs

ผลลัพธ์: สเปกจะถูกจัดเก็บและซิงค์ไว้ที่ Store กลาง แต่เมื่อสั่ง Apply ตัว AI จะแก้ไขโค้ดใน Repo ปัจจุบันให้อัตโนมัติ

17 การแก้ปัญหาที่พบบ่อย (Troubleshooting & FAQ)

Q: AI เริ่มเขียนโค้ดทันทีในขั้นตอน Propose หรือไม่? +
ไม่ครับ OpenSpec มีกฎเหล็กว่าในขั้นตอน Propose ตัว AI จะหยุดทันทีที่สร้างเอกสารวางแผนเสร็จ เพื่อรอให้คุณตรวจสอบก่อนเสมอ จะเริ่มเขียนโค้ดก็ต่อเมื่อได้รับคำสั่ง Apply เท่านั้น
Q: หลังรัน init แล้วใน IDE ไม่เห็นคำสั่ง Slash Commands? +
ให้ทำการ Restart หรือ Reload Window ของโปรแกรม IDE (เช่น Cursor หรือ Antigravity) 1 ครั้ง เพื่อให้ตัวโปรแกรมโหลดไฟล์ Workflows ใหม่เข้ามาในสภาพแวดล้อม
Q: นำคู่มือนี้ไปเผยแพร่ต่อจะผิดลิขสิทธิ์หรือไม่? +
ไม่ผิดลิขสิทธิ์ครับ เนื่องจากโครงการ OpenSpec เผยแพร่ภายใต้สัญญาอนุญาต MIT License ซึ่งอนุญาตให้ทำซ้ำ ดัดแปลง แปลภาษา และเผยแพร่ได้อย่างเสรี เพียงแค่ต้องคงข้อความประกาศลิขสิทธิ์ (Attribution) ของผู้พัฒนาต้นทางไว้ด้วย
